# Бот для Telegram-канала со скидками и новостями об играх

Бот сам проверяет скидки в **Steam**, **GOG** и **Epic Games Store**,
бесплатные игры в Epic Games Store, а также свежие новости с игровых
сайтов — и публикует всё новое в ваш Telegram-канал на русском языке,
с ценами в 5 валютах. Работает бесплатно на GitHub Actions — свой сервер
не нужен.

**Если вы уже развернули более раннюю версию бота** — переходите сразу к
разделу [«Обновление уже работающего бота»](#обновление-уже-работающего-бота).
Первоначальная установка с нуля — в самом низу инструкции.

## Если что-то не так: где реально искать логи

Панель **Annotations** на странице запуска (со значком ⚠️ / ❌) показывает
только то, что GitHub явно считает предупреждением или ошибкой уровня
самого runner'а (например, "Node.js 20 is deprecated" — это не про бота,
а общее уведомление GitHub про версию окружения, можно игнорировать).
**Все реальные диагностические сообщения самого бота — в другом месте:**

1. Откройте конкретный запуск во вкладке **Actions**.
2. Кликните на job **run-bot** (не на "Annotations").
3. Разверните шаг **Run bot** (стрелка слева от названия шага).
4. Здесь построчный вывод: сколько скидок/новостей найдено, сколько
   новых, сколько обработано, сколько отправлено, сколько заняло по
   времени — именно это стоит присылать мне, если что-то выглядит не так.

## Что исправлено в этом обновлении

0. **Критический баг: GOG никогда не публиковал ни одной скидки, с самого
   начала работы этой функции.** По присланным логам выяснилось: GOG
   отдаёт процент скидки строкой вида `"-95%"` (с минусом и знаком
   процента), а не числом, как предполагалось без возможности проверить
   это вживую. Из-за этого `int()` падал на КАЖДОЙ без исключения игре
   GOG, и весь список скидок GOG отбрасывался целиком — молча, без
   падения всего бота (поэтому внешне выглядело как "GOG просто ничего
   не находит", а не как явная ошибка). Теперь используется устойчивый
   разбор, который понимает такой формат; проверено на реальных данных
   из присланного лога (Cris Tales Original Soundtrack, A Plague Tale:
   Innocence и другие — теперь корректно распознаются и считаются).
1. **Вероятная причина странной новости на английском с текстом об
   ошибке**: бесплатный переводчик иногда возвращает не перевод, а
   служебное сообщение об ошибке (лимит запросов, недоступность и т.п.),
   но НЕ поднимает исключение в Python — код принимал это сообщение за
   настоящий перевод и публиковал как есть. Теперь результат перевода
   проверяется (похоже ли это на ошибку или на реальный перевод), и при
   подозрении на ошибку делается повторная попытка; если и она
   неудачна — публикуется оригинал на английском, а не мусорный текст.
2. **Защита от долгих запусков при большом наплыве новых скидок** (например,
   сразу после снижения порога — при таком единоразовом всплеске одна
   игра требует до 5 отдельных запросов цены, и десятки новых скидок разом
   могли растянуть один запуск на много минут). Теперь за один запуск с
   каждой платформы обрабатывается не больше 10 новых скидок (самые
   крупные — в приоритете), остальные подхватятся в следующих запусках
   через 5 минут — без потерь, просто более плавно.
3. Добавлены более подробные логи (сколько найдено/ново/обработано/
   отложено по каждой платформе, длительность запуска) — если ситуация
   вроде "скидки не постятся" повторится, в логе шага **Run bot** будет
   гораздо понятнее, на каком именно этапе и почему.
4. **Epic Games (обычные скидки) — более понятная диагностика.** В логе
   встретилась ошибка `Expecting value: line 1 column 1 (char 0)` — это
   Python пытался разобрать как JSON пустой/нестандартный ответ. Похоже,
   защита Epic от ботов иногда блокирует запросы именно с серверов GitHub
   Actions. Добавил повторную попытку на случай временного сбоя и более
   понятное сообщение в лог. Если ошибка продолжит появляться регулярно —
   это, вероятно, ограничение самого источника, а не бага в коде; тогда
   разумным решением будет отключить конкретно эту функцию, оставив
   рабочую еженедельную бесплатную игру Epic — она использует другой,
   не защищённый эндпоинт и стабильно работала с самого начала.

Вы заметили, что бот срабатывает не каждые 5 минут, а примерно раз в
1.5–2 часа (иногда пропуская и это). Разобрался — и вот честный разбор:

**Причина не в коде бота, а в самом GitHub Actions.** Расписание
(`schedule` в workflow-файле) — это отдельный, известный своей
ненадёжностью механизм GitHub: множество разработчиков в официальном
форуме GitHub жалуются на ровно то же самое — ручной запуск (`workflow_dispatch`)
работает всегда, а расписание срабатывает через раз, с многочасовыми
разрывами, безо всякой связи с настройками конкретного репозитория. Это
подтверждено самим GitHub как временами платформенная проблема, а не
что-то, что можно починить правкой одного YAML-файла.

**Из-за этого «ломался» и таймер очереди.** Таймер — не сломан сам по
себе: он публикует не чаще раза в 10–15 минут именно на каждой ПРОВЕРКЕ.
Но если проверка происходит раз в 2 часа вместо раза в 5 минут, то за
эти 2 часа накапливается несколько новых скидок — а таймер отпускает из
очереди максимум одну запись каждого типа за один запуск. То, что
выглядело как «всё выгружается разом раз в 2 часа», — это и есть таймер,
просто он может действовать только в те редкие моменты, когда бот вообще
запускается. Почини́ть саму частоту публикации бессмысленно, пока не
чинится частота запуска — поэтому решение ниже.

### Решение: внешний бесплатный планировщик вместо (точнее, в дополнение к) расписания GitHub

Идея: заставить GitHub запускать workflow так же, как при нажатии кнопки
«Run workflow» вручную, но делать это будет не человек, а внешний
бесплатный сервис — каждые 5 минут, по расписанию, которое не зависит от
внутреннего планировщика GitHub Actions.

#### Шаг 1. Создайте токен доступа (Personal Access Token)

1. Откройте [github.com/settings/tokens?type=beta](https://github.com/settings/tokens?type=beta)
   (это раздел **Settings → Developer settings → Personal access tokens → Fine-grained tokens**).
2. **Generate new token**.
3. **Token name** — любое, например `game-deals-bot-trigger`.
4. **Expiration** — поставьте максимальный срок (например, 1 год) — по
   истечении просто создадите новый токен и обновите его в сервисе-планировщике.
5. **Repository access** → **Only select repositories** → выберите ваш
   репозиторий с ботом.
6. **Permissions** → **Repository permissions** → найдите **Actions** →
   поставьте **Read and write**.
7. **Generate token** внизу страницы.
8. Скопируйте токен (строка вида `github_pat_11A...`) — он показывается
   только один раз, сохраните его во временную заметку, он понадобится
   на следующем шаге.

#### Шаг 2. Зарегистрируйтесь на бесплатном сервисе-планировщике

Подойдёт [cron-job.org](https://cron-job.org) — бесплатно, без банковской
карты, поддерживает нужные нам настройки (свои заголовки запроса и тело
запроса).

1. Зарегистрируйтесь и подтвердите почту.
2. **Create cronjob**.
3. **Title** — любое, например `Game Deals Bot trigger`.
4. **URL**:
   ```
   https://api.github.com/repos/ВАШ_ЛОГИН/ВАШ_РЕПОЗИТОРИЙ/actions/workflows/bot.yml/dispatches
   ```
   (замените `ВАШ_ЛОГИН` и `ВАШ_РЕПОЗИТОРИЙ` на реальные — их видно в
   адресной строке, когда вы открываете свой репозиторий на github.com).
5. **Execution schedule** → **Every 5 minutes** (или ближайший доступный
   вариант на бесплатном тарифе — обычно есть).
6. Найдите раздел **Request method / Advanced** (может называться
   по-разному в зависимости от версии интерфейса) и укажите:
   - **Method**: `POST`
   - **Headers** (добавить три):
     - `Authorization` → `Bearer ВАШ_ТОКЕН_ИЗ_ШАГА_1`
     - `Accept` → `application/vnd.github+json`
     - `Content-Type` → `application/json`
   - **Body / Request body**:
     ```json
     {"ref":"main"}
     ```
     (если ваша основная ветка называется не `main`, а, например, `master` —
     укажите её здесь).
7. Сохраните (**Create** / **Save**).

#### Шаг 3. Проверьте

На cron-job.org обычно есть кнопка **Test run** / **Execute now** — нажмите
её. Затем откройте вкладку **Actions** в репозитории на GitHub — должен
появиться новый запуск с пометкой "workflow_dispatch". Если появился —
всё настроено верно, и дальше сервис будет дёргать бота каждые 5 минут
сам, независимо от того, работает ли в этот момент штатное расписание
GitHub или нет.

Родное расписание GitHub (`schedule` в `bot.yml`) я оставил включённым —
оно не мешает и иногда тоже будет срабатывать, просто теперь бот не
зависит от него как от единственного источника запуска.

## Частота проверки и публикации

Проверка источников происходит каждые ~5 минут (при настроенном внешнем
планировщике — см. выше). Публикация — по приоритету:

| Приоритет | Что это | Когда публикуется |
|---|---|---|
| 🔥 | Крупная скидка (от 70%, настраивается) | Практически сразу после появления |
| 🆓 | Игра стала бесплатной | Практически сразу после появления |
| 💰 | Обычная скидка (40–69%) | Из очереди, не чаще раза в 10–15 минут |
| 📰 | Обычная игровая новость | Из очереди, не чаще раза в сутки |

Новости намеренно сделаны редкими (раз в сутки) — канал в первую очередь
про скидки, и не должен конкурировать с ними за внимание подписчиков.
Порог скидки снижен с 50% до 40%, чтобы скидок в канале было больше.

Обе цифры (0/10-15 мин/сутки и 40%/70%) — обычные настройки в `main.py`,
меняются одной правкой числа, см. таблицу в разделе «Как что-то настроить».

## ⚠️ Важно про расписание GitHub Actions и бесплатный лимит

У бесплатного GitHub есть лимит **2000 минут работы Actions в месяц**
для **приватных** репозиториев (для **публичных** — лимита нет вообще).
При проверке каждые 5 минут (через внешний планировщик, см. выше) это
реально приблизит вас к границе лимита для приватного репозитория.

**Рекомендация: сделайте репозиторий публичным.** Код бота не содержит
ничего секретного — токен бота и ID канала хранятся отдельно, в Secrets,
и в самом коде их не видно. Сменить видимость: **Settings** → в самом
низу **Danger Zone** → **Change visibility** → **Make public**.

Если оставить приватным и лимит всё же кончится — ничего не сломается
безвозвратно, просто автоматические запуски приостановятся до обнуления
лимита в начале следующего месяца.

## Будет ли бот работать постоянно?

Да, бессрочно и бесплатно, если сделать репозиторий публичным (см. выше)
и настроить внешний планировщик (тоже выше) — это снимает оба реальных
ограничения (лимит минут и ненадёжность родного расписания GitHub).
Остаётся:

- **Автоотключение расписания GitHub при 60 днях полного бездействия
  репозитория.** Не относится к внешнему планировщику — тот дёргает
  `workflow_dispatch`, а не `schedule`, и это ограничение не затрагивает.
  Бот к тому же сам коммитит `state.json`, что тоже засчитывается как
  активность.
- **Токен из Шага 1 имеет срок действия** (вы сами его выбрали при
  создании, например 1 год) — по истечении нужно будет создать новый и
  обновить в настройках cron-job.org. Это единственное, что требует
  ручного вмешательства раз в выбранный срок.

Сам GitHub Actions и Telegram Bot API постоянны и не имеют "срока
годности" сверх перечисленного.

## Обновление уже работающего бота

1. Разархивируйте присланный `game-deals-bot.zip`.
2. В репозитории на GitHub: **Add file** → **Upload files** → перетащите
   всё содержимое папки `game-deals-bot` (включая `.github`).
3. **Не загружайте `state.json` из архива** — если он попал в список
   загружаемых файлов, уберите его (крестик рядом с файлом) перед commit.
   Ваш текущий `state.json` полностью совместим с новой версией, ничего
   вручную мигрировать не нужно.
4. **Commit changes**.
5. Новых секретов (токенов ботов, ключей API) добавлять не нужно.
6. Если ещё не настроен внешний планировщик — самое время настроить
   (раздел выше) — без него частота работы бота останется ненадёжной.
7. Проверьте: вкладка **Actions** → **Game Deals Bot** → **Run workflow**
   → через минуту-две посмотрите лог шага **Run bot** (не должно быть
   `Traceback`) и загляните в канал.

## Ограничения и как к ним относиться

- **Дата окончания скидки есть только у Epic Games.** У Epic это поле
  приходит напрямую от их API (то же самое, которым уже давно и надёжно
  пользуется еженедельная бесплатная игра). У Steam и GOG в их
  официальных публичных API такого поля просто нет — точную дату можно
  получить только выгрузкой HTML-страницы магазина, что значительно
  менее надёжно и легко ломается при любом изменении вёрстки сайта. Не
  стал добавлять это ради красивой строки, которая будет регулярно
  переставать работать без предупреждения. Если для вас это критично
  важно именно для Steam — дайте знать отдельно, обсудим компромиссы.
- **Перевод новостей автоматический и не идеальный** — названия игр,
  которые бот уже видел среди скидок, и стандартные игровые термины
  защищены от перевода, но не любое редкое имя человека/студии.
- **Мультивалютность GOG — "лучшее из возможного"**, у GOG нет
  официального API для цен в разных валютах, и, по отзывам сообщества,
  единственный найденный неофициальный вариант нестабилен. Меньше
  валютных строк для GOG, чем для Steam — это ожидаемо.
- **Обычные скидки Epic Games Store** — самая новая и наименее
  проверенная часть проекта (см. `sources/epic.py`), но её сбои не
  затрагивают остальные источники.
- **PlayStation Store, Xbox и Nintendo eShop** по-прежнему не включены —
  нет стабильного бесплатного источника данных.

## Как что-то настроить

Правки — в файле `main.py`, раздел `НАСТРОЙКИ` (или в указанном файле).
Через браузер на GitHub: открыть файл → карандаш "Edit" → Commit changes.

| Что настроить | Где | Значение сейчас |
|---|---|---|
| От какой скидки постить вообще | `MIN_DISCOUNT_STEAM/GOG/EPIC` | 40 (%) |
| От какой скидки считать "горячей" (🔥) | `HOT_DISCOUNT_THRESHOLD` | 70 (%) |
| От скольких скидок одного издателя склеивать в один пост | `BUNDLE_MIN_COUNT` | 4 |
| Интервал публикации обычных скидок (💰) | `TIER_INTERVAL_SECONDS["deal"]` | 720 сек (12 мин) |
| Интервал публикации новостей (📰) | `TIER_INTERVAL_SECONDS["news"]` | 86400 сек (сутки) |
| Сколько сообщений максимум слать за один запуск | `MAX_POSTS_PER_RUN` | 10 |
| Какие новостные сайты использовать | `sources/news.py`, `FEEDS` | RPS, PC Gamer, PCGamesN |
| Как часто дёргает бота внешний планировщик | настройки на cron-job.org | каждые 5 минут |

## Первоначальная установка (если разворачиваете бота впервые)

### Шаг 1. Создайте Telegram-канал (если его ещё нет)

В Telegram: **Новый канал** → название → сделайте публичным, придумайте
юзернейм (например `@my_game_deals`).

### Шаг 2. Создайте Telegram-бота и получите токен

**@BotFather** → `/newbot` → следуйте инструкциям → сохраните токен
(строка вида `123456789:AAExampleToken...`). Никому не показывайте.

### Шаг 3. Добавьте бота администратором канала

Настройки канала → **Администраторы** → **Добавить администратора** →
найдите бота → право **публиковать сообщения**.

### Шаг 4. Узнайте ID канала

Публичный канал — юзернейм с `@` (например `@my_game_deals`). Приватный —
перешлите сообщение из канала боту **@userinfobot**, он покажет числовой
ID вида `-1001234567890`.

### Шаг 5. Разместите код на GitHub

[github.com](https://github.com) → **New repository** → **Add file** →
**Upload files** → перетащите содержимое папки `game-deals-bot` (включая
`.github`) → **Commit changes**.

### Шаг 6. Добавьте секреты

**Settings** → **Secrets and variables** → **Actions** →
**New repository secret**: `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID`
(значения из шагов 2 и 4).

### Шаг 7. Настройте надёжный автозапуск

Обязательно выполните раздел [«Главное в этом обновлении: надёжный
автозапуск»](#главное-в-этом-обновлении-надёжный-автозапуск) выше — без
него бот будет запускаться крайне нерегулярно (это ограничение самого
GitHub, не зависящее от того, разворачиваете вы бота впервые или
обновляете).

### Шаг 8. Запустите и проверьте

Вкладка **Actions** → разрешите workflow, если попросит → **Game Deals
Bot** → **Run workflow**. Проверьте лог и канал.
